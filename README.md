# Run and deploy your AI Studio app

This contains everything you need to run your app locally.

View your app in AI Studio: https://ai.studio/apps/7b0a7816-b77d-43fb-8a29-5acaf71b6b0f

## Run Locally

**Prerequisites:** Node.js 20.18.1 or later


1. Install dependencies:
   `npm install`
2. Copy `.env.example` to `.env`. You can connect Gemini, OpenAI, and OpenRouter in the app after starting it, or set `GEMINI_API_KEY`, `OPENAI_API_KEY`, and/or `OPENROUTER_API_KEY` here. Keep `.env` untracked.
3. Run the app:
   `npm run dev`

> **Note on Server Changes:** If you edit API routes or backend code in `server.ts` or `src/domainGeneration.ts`, restart the development process (`npm run dev`) so Node reloads the updated API handlers.

## AI providers

Gemini, OpenAI, and OpenRouter are supported independently for drafting and review/analysis. In **Models → API connections**, paste a key for any of the three providers and select **Connect**. The server validates the key with that provider, saves it to the untracked `.env` with owner-only permissions, and activates it immediately. Use the same form to update a saved key. Key management requires opening the app on localhost; cross-origin and remote requests are rejected. No key is returned to the browser or stored in browser settings. Keys supplied manually through the server environment or `.env` require a server restart after changing them.

Each configured provider also has **Remove key**, which deletes its saved `.env` entry and clears its active server key immediately. Other provider keys and model choices are preserved. Removal disconnects this app; it does not revoke the key at the provider. Keys supplied by an external launcher must also be removed there to remain disconnected after relaunch.

In **Models**, choose **Drafting** or **Review & analysis**, then pick a **Provider** and search the **Model** dropdown. Gemini uses the existing presets; OpenAI and OpenRouter load their model catalogs through the server. Picking a provider does not change the saved selection until you choose a model. Model changes reset reasoning to **Auto**. An exact model ID can still be selected from the search field when it is not in the catalog. **API connections** opens a separate setup/status view. Settings persist in the existing browser-local model settings, including existing Gemini selections. OpenAI IDs are stored as `openai:<model-id>` and OpenRouter IDs as `openrouter:<provider/model-id>`.

The analysis choice covers editorial planning, review, samples, voice blueprints, domain knowledge, feedback learning, portfolio discovery, and scanned-PDF extraction. Local document extraction runs first, and `localOnly` uploads stay local. Choose a model with structured-output support for analysis and PDF support for scanned documents. Unsupported models/settings return an error; new providers never fall back to Gemini or another service. Writing failures preserve the existing draft, and review failures preserve the generated result with an unavailable review.

The model catalog excludes dedicated non-text endpoints where the provider exposes enough information; appearing in the list does not guarantee every reasoning level, structured-output mode, or PDF input is supported. A failed catalog request leaves the saved model unchanged and offers retry or exact-ID entry.

**Reasoning** varies with the selected provider and model. OpenRouter choices come from the live catalog’s `reasoning.supported_efforts` metadata, including new effort names; models without an effort selector use Auto. Direct OpenAI and Gemini model lists do not expose these choices, so known models use documented per-model options in `src/modelChoice.ts` ([OpenAI model documentation](https://developers.openai.com/api/docs/models), [Gemini Generate Content thinking](https://ai.google.dev/gemini-api/docs/generate-content/thinking), [OpenRouter effort metadata](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens)). Unknown external models show provider effort values with an explicit support-unverified note. **Auto** omits the effort parameter; **None** explicitly requests no reasoning where supported. The server sends the exact selected effort (`reasoning_effort` for OpenAI, `reasoning.effort` for OpenRouter, `thinkingConfig.thinkingLevel` for Gemini), rejects known incompatible settings, and never lowers an effort silently. An older saved effort that is no longer listed remains visible for correction.

Both new providers use their documented Chat Completions APIs: [OpenAI](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) and [OpenRouter](https://openrouter.ai/docs/quickstart). Connection validation uses the [Gemini model-list endpoint](https://ai.google.dev/api/models#method:-models.list), OpenAI's model-list endpoint, and OpenRouter's [current-key endpoint](https://openrouter.ai/docs/api/api-reference/api-keys/get-current-api-key); it does not generate text or guarantee available credit or access to every model. `/api/health` reports whether each server key is configured. Provider errors do not expose keys or raw upstream response bodies.

## Workflow

The numbered writing workflow is:
**1. Writing Samples → 2. Voice Blueprint → 3. Draft & Brief → 4. Domain Knowledge → 5. Rewrite Studio**

The app opens on Writing Samples. Each Continue button advances to the next stage. Samples supply the voice blueprint; the draft and brief supply the source context for domain knowledge; Studio then creates the edit plan, accepts approval, and rewrites. Existing samples, voice, and knowledge remain reusable, and individual tabs remain accessible.

Navigation remains freely available across all tabs at any time without a forced wizard.

**Supported use:** PersonaScript is a desktop and laptop application. Phone use and mobile optimization are out of scope. Design and verify changes for desktop and laptop workflows; do not add mobile layouts or run mobile-specific checks unless explicitly requested.

## Writing pipeline and project brief

Each writing action sends the complete enabled sample corpus (up to 100,000 characters) to the selected writing model. Planned writing then runs two calls with the selected analysis model: a source-only audit of the approved plan followed by prose review. Legacy unplanned API writing retains one prose-review call. Samples are used as voice evidence; the draft and optional project brief supply facts and qualifications. Planning and review receive no writing corpus or voice profile. Review findings are advisory, and a review failure keeps the generated draft.

- **Draft & Brief view**: The dedicated **Draft & Brief** tab manages the raw **Original draft**, optional **Project brief**, optional **Reader and purpose** guidance, and optional **Standing preferences**. Draft, brief, and reader-and-purpose start empty for a new browser origin; standing preferences start from their saved defaults. `WritingAssistantContext` restores a previously saved working copy when available. Domain generation accepts up to 100,000 characters each for the draft and brief without truncation; the brief input also enforces its 100,000-character limit (`PROJECT_BRIEF_MAX_CHARS`), while reader-and-purpose guidance is limited to 2,000 characters and standing preferences to 4,000. Draft, brief, reader-purpose guidance, standing preferences, and the current result are saved locally with the working copy and restored after navigation, refresh, or a development remount. Over-limit reader-purpose text remains recoverable in the working copy and through **Download working copy** while generation reports the validation error; shortening it clears the error without silently truncating the saved input. Clearing any input saves the empty value; restoration does not substitute an older source from history.
- **Context roles & boundaries**: The draft is the editorial target and source account; the project brief supplies case context and professional rationale (not mandatory text or behavior directives); reader-and-purpose guidance selects relevance, emphasis, explanation, and organization without adding facts or changing source claim strength; writing samples supply voice only. Prompts enclose factual reference data such as the brief in untrusted data delimiters (`<project-brief>`) and instruct the models to ignore embedded commands, while reader-and-purpose guidance remains subordinate editorial control.
- **Review suggested edits**: In Studio, choose **Prepare plan**. The selected Review & analysis model reads the draft, brief, reader and purpose, the rewrite instructions, and standing preferences, and proposes the smallest useful set of decisions — generally one per paragraph, split only where treatment or claim limits differ. The panel shows one flat list in draft order: source conflicts first with both quotations, then every cut, shorten, and keep that carries a claim limit, each as one row with its paragraph references. Identical repeated decisions appear once with all their references; ordinary keeps collapse to a count that expands on demand. Display grouping never changes the stored plan. **What the opening should do** is editable inline above the list. Each row edits in place — instruction, treatment, limit, exact source wording, paragraph, and conflict evidence — without opening a separate view. Incomplete decisions and lost anchors are flagged and must be fixed before rewriting; **Refresh plan** regenerates the proposal and **Add a decision** extends it. New plans must cover every source paragraph. **Approve and rewrite** validates and sends the full approved snapshot, including collapsed and grouped decisions. When the draft, brief, reader and purpose, rewrite instructions, or standing preferences change, a warning names what changed and approval is required again. Failed planning or writing preserves previous work.
- **Standing preferences**: **Standing preferences** are edited in **Draft & Brief**, saved in the existing browser working copy, and apply across cases. The defaults preserve named design principles and illustrations, allow confident professional reasoning, and keep results attributed to their recorded program/team. The field is editable or clearable and limited to 4,000 characters; Studio notes when they are included in a plan. Oversized restored working text remains available for correction; it is not silently discarded. Saved versions retain the exact preferences used for follow-up edits. Preferences are editorial guidance, not factual evidence.
- **Writing settings**: Studio settings stay flat and visible — no menu inside a disclosure. A source rewrite shows rewrite strength and the fact locks (names and terms, numbers, direct quotes, section order, heading wording, plus optional protected text); follow-up edits show the same locks. The rewrite request has one field per mode: **Instructions for this rewrite** above the plan for source rewrites (planning reads it, and changing it requires approval again), and **What should change?** for edits, where a note appears when source-rewrite instructions still apply. Tone adjustments live in **Voice Blueprint**; standing preferences live in **Draft & Brief**; Studio only surfaces a warning with a link when the voice blueprint needs updating and does not repeat domain-topic switches. Changing settings does not generate text. **Apply changes** can apply changed preservation locks without an additional typed request. Writer/reviewer configuration has one location, **Models** in the global header.
- **Editorial scope**: The approved list is the writer's primary editorial constraint and the reviewer's checklist. Keep preserves an idea's substance; shorten retains the specified substance in less space; cut removes the idea, including paraphrases. The brief may clarify approved ideas without replacing the draft's narrative. Specific preservation locks still apply; the reviewer should identify conflicts with decisions. New explicit refinement or selection requests may supersede decisions within the requested scope. Planning, approval, and review do not guarantee editorial quality.
- **Planning API**: `/api/plan-draft` accepts draft, optional projectBrief, readerPurpose, editorialPreferences, and customInstructions (the rewrite request), and model/reasoningLevel. It uses structured output with no model fallback. Planning allows up to ten minutes for the selected model and reasoning depth, cancels upstream work if the request connection closes, and keeps the draft and previous plan on failure. Draft and brief are limited to 100,000 characters each; reader and purpose to 2,000; standing preferences to 4,000; the rewrite request to 100,000. New generated decisions must have complete fields, source phrases anchored to their numbered draft paragraph, and coverage of every paragraph. Structured source-conflict quotes must occur in their respective draft and brief. The server strips recognized PDF furniture before planning and writing; actual headings, captions, and body figures remain source text. Exact quote validation proves quote membership, not semantic truth. Writing endpoints validate supplied approval snapshots against their exact source context. Legacy API clients and saved versions without a plan remain supported; new full rewrites through Studio require an approved plan.
- **Voice and qualitative fidelity**: For the writer, matching generated profiles contribute numeric style metrics and expression-scoped user directives; generated vocabulary lists, pacing descriptions, profile names, and manifestos are excluded from writer and reviewer guidance. The raw corpus remains surface-style evidence. Fidelity rules cover grammatical intention (including purpose clauses and role/task constructions) and degree changes such as manner adverbs recast as absolute qualities. Reader-and-purpose guidance should include what the reader already knows so the writer can distinguish necessary explanation from redundant background. These instructions do not guarantee model compliance.
- **Local preservation**: Local checks accept numbers and direct quotations supported by the project brief without false-positive unexpected warnings, while strictly verifying that explicit preservation locks on source numbers and quotations remain satisfied.
- **Document upload**: Supports uploading `.md`, `.txt`, `.docx`, and `.pdf` files into the brief or draft. Draft and brief extraction uses local-only parsing; scanned PDFs without extractable text show an error instead of invoking remote OCR. Upload failures preserve the previous input, and generation waits for pending source uploads.
- **Rewrite Studio**: Entering Studio, including from Domain Knowledge, shows the **Original draft** from the current Draft & Brief inputs and a source-rewrite action. It never generates on entry or substitutes a saved rewrite. A dated **Open saved rewrite** control and **History** retain access to previous work. After an explicit writing action, the document is labelled **Rewritten draft**; reopening an existing result labels it **Saved rewrite**, with its version and creation date. **New rewrite from source** returns to the original source and preparation controls. The document stays on the left; one panel on the right holds the active editing, review, or source-preparation task. The writing action stays visible while the plan and settings scroll. **Details** groups the saved source, brief, reader/purpose, edit plan, settings, models, and change summary.

## Studio models, review, and recovery

- **Writer and reviewer:** The existing writing model writes full drafts, quick adjustments, and selection edits. **Review & analysis** selects the existing analysis model for draft review, sample analysis, voice blueprints, and domain knowledge. Both choices are configured in the header’s **Models** panel; **Change reviewer** opens that same panel. Changes apply to the next request; a result records its actual writer and its actual reviewer, or the requested reviewer when review was unavailable.
- **Editorial expectation:** A complete rewrite should reconstruct a weak opening and cut dispensable exposition when appropriate, without requiring a line edit. An explicit editorial request takes precedence over general intensity and voice preferences, subject to factual fidelity and explicit locks. Keeping section order does not lock the opening or argument sequence within a section. A selection edit is useful when only one passage should change; quick adjustment revises the current complete result, while a new full rewrite starts from Draft & Brief. Saving a voice note updates the profile immediately, with visible saving, saved, and retry states. A failed profile save never repeats a completed prose edit. Profile updates and applied-note IDs are saved together before removing the note, preventing replay from older history. On upgrade, the old feedback queue is retired automatically without running learning again or changing profile preferences. Its records are retained with the current version before clearing the queue. Retirement persists across reloads and version restores; it does not claim to reconstruct how many times earlier learning ran.
- **Editing requests:** Open a saved or newly completed rewrite, describe a change in **What should change?** — the single request field for edits — or adjust the preservation locks, then choose **Apply changes**. Source-rewrite instructions continue to apply to follow-up edits and are shown as a note; change them under **New rewrite from source**. Highlighting text uses the same form and exposes **Selected passage / Entire draft** scope; the selected-passage route preserves surrounding text. Enter adds a new line; Ctrl/Cmd + Enter submits. **Also save this as a style rule** reveals the optional feedback category and a separate note-only save. Ordinary edits do not save voice notes. Each failed voice-note operation has one retry, which never repeats a completed prose edit. Failed edits preserve the request and current prose.
- **Review:** Source-audit findings survive a clean or failed later prose review. An unavailable review retains the generated draft. The document’s **Review** control indicates issues or unavailable review. It opens findings as one flat list beside the document, with paired source/rewrite passages when saved evidence supports them. **Edit this issue** prepares an editable request; **Mark reviewed** is session-only and changes no prose or saved review. Repeated identical findings are consolidated while distinct concerns remain separate. Count-only number, quotation, and heading differences stay under **Text checks** with source context; they do not establish factual substitutions. Praise, commentary, passed checks, and reviewer identity remain under a separate disclosure. The reviewer checks each approved decision, source claim strength, the opening job, and whether the requested editorial improvement occurred. It receives no voice corpus or profile and does not grade imitation; incremental reviews also receive the previous text and selection scope. Review is advisory and does not automatically repair the draft. Prompt delivery and deterministic tests do not prove that a model will fulfill an editorial request.
- **Version history:** `personascript_history_v2` remains the browser-local owner of the last 20 completed versions. Every new rewrite/refinement/selection edit gets a distinct ID and timestamp; saved edits record their request and parent version. Duplicate legacy IDs are normalized without discarding text, but missing old edit types/timestamps cannot be reconstructed. Preview leaves current work in place. **Continue from this version** switches the current result, preserving the outgoing result and leaving Draft & Brief inputs and current model/voice controls untouched. Every planned version saves the exact approved list and source snapshot, visible in the result and version preview. Follow-up edits to planned or reopened versions use their original draft, saved brief, saved reader and purpose, standing preferences, and saved decisions. Legacy unplanned live results retain the previous behavior of using the current brief and reader and purpose. A new full rewrite uses the current source inputs.
- **Working copy:** `personascript_workspace_v1` stores the current draft, brief, reader and purpose, standing preferences, proposed/approved editorial decisions (including incomplete edits), result, additional instructions, intensity, source-context choice, and unsaved or earlier voice notes. This is the current-session snapshot, not a second version history. On first use after upgrading, if no working-copy snapshot exists, the latest saved version can reopen as the current result without filling the draft/brief inputs from an old project. An explicit empty saved working copy stays empty.
- **Save status and failure:** Saving is local to this browser profile and exact origin; it is not a server backup or cross-device sync. `http://0.0.0.0:3000`, `http://localhost:3000`, and other ports have separate storage. The app shows saved/error status and can download the working copy plus all versions currently held in memory as readable JSON, including versions whose history save failed. If a write fails, the last successful saved value is retained and the current work stays in memory; the app warns before leaving while a save error is present. Malformed saved data is left untouched rather than overwritten with empty defaults. A preset reset restores samples/voice/tone/model settings and keeps drafts and history. Clearing browser/site data still removes local saves; keep a downloaded copy for independent retention.

## Adding writing samples

Adding pasted text or an extracted document stores the sample locally without an AI request. Each sample can be analyzed separately with **Analyze sample**. **Cancel analysis** stops waiting and aborts the provider connection while preserving the sample and any previous analysis. Sample analysis allows up to ten minutes, including the provider request, and then stops with a retry message. The selected model and reasoning effort are preserved. Reloading clears interrupted analysis indicators; it does not restart analysis. A provider may still charge for work performed before cancellation.

## Development while the app is in use

A different port is **not source isolation**. Two Vite servers watching this checkout can both hot-reload after one source edit. Changing the context provider's hooks or exports can remount it and clear state that has not been saved.

Before changing watched files behind an actively used instance, identify its checkout and exact origin, protect the user's work, and establish a safe apply point. When this cannot be done, prepare and verify the change in an explicitly authorized ordinary source copy outside the watched directory (or an explicitly authorized Git worktree). Copy only required source/config/tests; do not copy `.env`, credentials, browser data, or unrelated private material. Use deterministic providers and a separate QA origin. Apply the verified patch to the live checkout only at the agreed safe point. Do not restart the user's server without authorization; a server restart is required for backend prompt changes.

Verify draft/brief/current-result restoration through both page reload and provider remount, intentional clears, version switching, legacy history, and storage read/write failures. Save-status checks must establish actual persistence, not merely that an effect ran or a label appeared.

## Domain and product knowledge

The Domain view configures disciplinary concepts and product reference knowledge:

- **Concept recognition**: Disciplinary concepts (such as information hierarchy, user comprehension, informed choice, product value, and conversion) help the model recognize and articulate thinking already present in drafts without forcing jargon or fabricating unperformed work.
- **Product reference knowledge**: Product notes supply factual background for interpreting product names, feature relationships, and historical periods. Product discrepancies are flagged as observations in the advisory review rather than silently altering source facts.
- **Source-aware generation & checkbox**: Domain knowledge generation optionally incorporates the active draft and project brief alongside configured disciplines. The **Use draft and brief** checkbox (session UI state, initially enabled) sends draft and brief text to the generation endpoint. Disabling the checkbox omits both inputs from outbound requests and prompts. The choice survives tab navigation. Only clicking a generation control sends a request; editing sources does not regenerate cards automatically.
- **Supported vs. adjacent concepts**: Generation identifies both source-supported concepts (clearly demonstrated by decisions described in the draft/brief) and plausible adjacent concepts (cross-disciplinary ideas that could expose explanatory gaps). With source context, every generated concept has a `(supported)` or `(adjacent)` label and a concise explanation of its relevance. These are model assessments, not verified facts. Cards and their labels are saved with the voice profile and reflect the source used at generation time; review or regenerate them when changing projects. Without source context, cards retain generic concept examples without source labels.
- **Factual boundary**: Adjacent concepts are possibilities for interpretation/questions, NOT evidence the author performed extra work, research, or testing. They do not become factual authority for writer or reviewer models; the reviewer is instructed not to treat the absence of adjacent concepts as omissions.
- **Topic single-ownership**: Topic content has single ownership; disabling or deleting a topic removes its prompt contribution without term leakage. Empty topic lists are preserved.
- **API generation and broad coverage**: Disciplinary topics and concepts are populated dynamically via `/api/generate-domain-knowledge`. Each card has **Regenerate** to refresh only its description, concepts, and rules, and **Clear** to empty that content while retaining its name, category, and enabled state. **Regenerate all** and **Clear all** affect the full topics section; **Generate domain knowledge** populates an empty section.
- **Scope controls**: The page-level active switch controls all knowledge on the Domain page; individual topic and product toggles choose included entries.

Domain generation and card regeneration allow up to ten minutes for the selected model and reasoning depth. Leaving the Domain view cancels the request. Failure or cancellation keeps existing knowledge intact.

OpenAI and OpenRouter generation use a request-specific Undici dispatcher so Node's default five-minute header/body timeout cannot override the app's deadline. The request's abort signal controls both waiting for headers and receiving the body; model discovery retains its separate short timeout.
